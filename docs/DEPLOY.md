# Перенос на другую машину и развёртывание

Документ описывает самый короткий путь: положить проект в git, забрать
его на новой машине, заполнить три строки настроек и запустить одну
команду.

---

## Коротко

Проект состоит из трёх частей, и переносятся они по-разному.

| Часть | Где живёт | Как переносится |
| --- | --- | --- |
| Код, образ, документация | git | `git clone` |
| Настройки: пароль, адреса | файл `.env` | вручную, в git не попадает |
| Данные: очередь и индекс | SQLite и Elasticsearch | снимок или сбор заново |

Развёртывание на чистой машине целиком:

```bash
git clone <адрес репозитория> /opt/sochi-search
cd /opt/sochi-search
bash deploy.sh          # создаст .env и остановится
nano .env               # заполнить три значения
bash deploy.sh          # соберёт и запустит
```

Всё остальное в этом документе — подробности к этим пяти строкам.

---

## 0. Что нужно от новой машины

| | Минимум | Комфортно |
| --- | --- | --- |
| Ядра | 2 | 4 и больше |
| Память | 6 ГБ | 8 ГБ и больше |
| Диск | 20 ГБ свободно | 50 ГБ |
| Система | Linux с Docker 20.10+ | — |

Индекс на 80 тысяч документов занимает около 8 ГБ, образы Docker — ещё
около 2 ГБ, остальное уходит на временные файлы при распознавании.

Установка Docker, если его нет:

```bash
# Ubuntu / Debian
apt-get update && apt-get install -y docker.io docker-compose-plugin curl

# RHEL / CentOS / Astra
dnf install -y docker docker-compose-plugin curl

systemctl enable --now docker
```

Одна системная настройка, без которой Elasticsearch не стартует:

```bash
sysctl -w vm.max_map_count=262144
echo 'vm.max_map_count=262144' >> /etc/sysctl.conf
```

Чтобы работать с Docker без `sudo`:

```bash
usermod -aG docker $USER
# после этого нужно выйти из системы и зайти заново
```

## 1. Один раз: положить проект в git

Присланный архив `sochi-search-2.5.0.tar.gz` — это уже готовый
репозиторий: внутри есть `.git` с историей, `.gitignore`, документация и
`deploy.sh`. Ничего собирать не нужно, только отправить на свой сервер
git.

Делать это можно с любой машины, где есть доступ к серверу git, —
рабочий сервер для этого трогать не нужно.

```bash
tar -xzf sochi-search-2.5.0.tar.gz
cd sochi-search

git log --oneline          # проверить, что история на месте
git remote add origin <адрес закрытого репозитория>
git push -u origin main
```

Репозиторий должен быть **закрытым**. Секретов в нём нет — `.env` туда
не попадает, — но публиковать устройство внутренней системы незачем.

### Что внутри

Около 12 МБ: код, файлы Docker, systemd-юниты, языковые модели
распознавания и документация. `.gitignore` исключает `.env`, `data/`,
`run/`, `backups/` и базы SQLite, поэтому ни пароль, ни данные в историю
не попадут.

Раскладка репозитория совпадает с тем, что лежит на рабочем сервере в
`/opt/sochi-search`: те же `app_v2/`, `crawler_v2/`, `ops/`, `systemd/`.
Добавились `docs/`, `deploy.sh`, `Dockerfile` и файлы `docker-compose`.

Проверить перед отправкой, что лишнего в коммите нет:

```bash
git status --porcelain | awk '{print $NF}' \
  | grep -E '(^|/)\.env$|\.sqlite3|^(data|run|backups)/' \
    && echo "ЛИШНЕЕ ВЫШЕ — проверьте .gitignore" \
    || echo "чисто: секретов и данных в коммите нет"
```

### Если своего сервера git нет

Тогда архив просто копируется на новую машину — всё работает так же:

```bash
scp sochi-search-2.5.0.tar.gz пользователь@новая-машина:/tmp/

# на новой машине
tar -xzf /tmp/sochi-search-2.5.0.tar.gz -C /opt
cd /opt/sochi-search
```

Дальше — сразу к разделу 3.

## 3. Заполнить настройки

```bash
bash deploy.sh
```

Первый запуск обнаружит, что файла `.env` нет, создаст его из образца и
остановится с подсказкой. Теперь его нужно заполнить:

```bash
nano .env
```

Обязательных значений три.

### ADMIN_USERNAME

Логин для входа в раздел управления. Можно оставить `admin`.

### ADMIN_PASSWORD_SHA256

Не сам пароль, а его отпечаток. Считается так — команда спросит пароль,
не показывая его на экране, и напечатает 64 символа:

```bash
python3 -c "import hashlib,getpass;print(hashlib.sha256(getpass.getpass().encode()).hexdigest())"
```

Эти 64 символа и вставляются в `.env`. Сам пароль нигде не хранится —
ни в файле, ни в резервных копиях.

> Пока строка пустая, раздел управления никого не пускает и отвечает
> ошибкой. Это сделано намеренно: молча пускать всех опаснее, чем не
> работать.

### API_BIND

Адрес, на котором поиск слушает запросы. Это и есть основная защита —
подробности в следующем разделе.

```bash
hostname -I        # покажет адреса машины
```

Из вывода берётся адрес внутренней сети — например `10.0.0.5` — и
вписывается в `.env`:

```
API_BIND=10.0.0.5
API_PORT=18084
```

### Если памяти больше 8 ГБ

Заодно стоит поднять память Elasticsearch — правило простое: половина
памяти машины, но не больше 30 ГБ.

```
ES_HEAP=6g
ES_MEM_LIMIT=9g
```

Всё остальное в `.env` можно не трогать.

## 4. Запустить

```bash
bash deploy.sh
```

Скрипт по шагам:

1. проверяет Docker, место на диске и память;
2. читает `.env` и предупреждает, если адрес выглядит опасно;
3. собирает образ приложения;
4. поднимает Elasticsearch и ждёт, пока тот ответит;
5. создаёт пустой индекс с нужной схемой;
6. запускает остальные контейнеры и печатает адреса.

Первый запуск занимает 5–10 минут: скачивается образ Elasticsearch
(около 1,5 ГБ) и собирается образ приложения. Повторные запуски —
меньше минуты.

В конце скрипт напечатает адреса:

```
Поиск:      http://10.0.0.5:18084/ui
Управление: http://10.0.0.5:18084/admin
```

Запускать `deploy.sh` можно сколько угодно раз — уже сделанное он не
трогает.

## 5. Доступ только из внутренней сети

Защита ставится в три слоя. Первого достаточно, остальные два — на
случай ошибки в первом.

### Слой 1: адрес прослушивания

Порт открывается только на том адресе, который указан в `API_BIND`.
Если это адрес внутренней сети, из интернета к поиску не подключиться,
даже зная порт: пакеты просто не дойдут до сокета.

```
API_BIND=10.0.0.5        правильно — только внутренняя сеть
API_BIND=127.0.0.1       ещё строже — только с самой машины
API_BIND=0.0.0.0         так не надо — все адреса, включая внешний
```

Проверить, что получилось:

```bash
ss -tlnp | grep 18084
```

В выводе должен стоять конкретный адрес, а не `0.0.0.0` и не `*`.

### Слой 2: Elasticsearch наружу не смотрит

Порт 9200 открыт только на `127.0.0.1` — с других машин к нему не
подключиться совсем. Приложение ходит к нему по внутренней сети Docker,
минуя порты хоста.

Это важнее, чем кажется: у Elasticsearch отключена собственная
авторизация, и всякий, кто дотянется до 9200, сможет читать и удалять
индекс.

```bash
ss -tlnp | grep 9200        # должно быть 127.0.0.1:9200
```

### Слой 3: межсетевой экран

```bash
# разрешить только свою подсеть
ufw allow from 10.0.0.0/24 to any port 18084 proto tcp
ufw deny 18084
ufw enable
```

Если в организации свой межсетевой экран — правило то же самое: порт
18084 открыт для внутренних подсетей и закрыт для всего остального.

### Что закрыто паролем, а что нет

| Адрес | Кто может открыть |
| --- | --- |
| `/ui`, `/search`, `/stats` | любой, кто дотянулся по сети |
| `/admin` и всё под ним | только по логину и паролю |

Так и задумано: поиском пользуются сотрудники, управлением — единицы.
Раздел управления спрашивает пароль формой на самом сайте; вход держится
12 часов, потом спрашивается снова. Смена пароля в `.env` автоматически
завершает все открытые сеансы.

## 6. Перенос данных со старой машины

Пропустите этот раздел, если новая машина собирает индекс с нуля.
Сбор занимает около суток на обход и заметно дольше на распознавание
сканов — поэтому перенос обычно выгоднее.

Переносить нужно две вещи: **очередь обхода** (какие адреса известны и
что с ними уже сделано) и **индекс** (сам текст документов).

### 6.1. Очередь обхода — один файл

На старой машине (та, что работает через systemd):

```bash
systemctl start sochi-search-backup.service
ls -lt /opt/sochi-search/backups/operational/ | head -3
scp /opt/sochi-search/backups/operational/sochi-search-backup-*.tar.gz \
    пользователь@новая-машина:/tmp/
```

На новой машине:

```bash
cd /tmp
tar -xzf sochi-search-backup-*.tar.gz
docker compose -f docker-compose.yml -f docker-compose.app.yml stop worker discovery ocr-1 ocr-2
docker cp crawl_state.sqlite3 sochi-search-api:/app/data/crawl_state.sqlite3
docker compose -f docker-compose.yml -f docker-compose.app.yml start worker discovery ocr-1 ocr-2
```

Воркеры останавливаются на время подмены, чтобы никто не писал в базу
во время копирования.

### 6.2. Индекс — снимок Elasticsearch

Снимок делается на работающем кластере, останавливать поиск не нужно.

**На старой машине** — зарегистрировать хранилище и снять снимок:

```bash
curl -XPUT "http://127.0.0.1:9200/_snapshot/move" \
  -H 'Content-Type: application/json' \
  -d '{"type":"fs","settings":{"location":"/snapshots"}}'

curl -XPUT "http://127.0.0.1:9200/_snapshot/move/full?wait_for_completion=true" \
  -H 'Content-Type: application/json' \
  -d '{"indices":"sochi_docs_v4_*","include_global_state":false}'
```

> Если старая машина ещё на прежнем `docker-compose.yml`, у неё нет тома
> `/snapshots`. Тогда сначала обновите файл из репозитория и
> перезапустите Elasticsearch:
> `docker compose -f docker-compose.yml up -d elasticsearch`

Забрать снимок из тома в обычный файл:

```bash
docker run --rm \
  -v sochi-search_essnapshots:/s \
  -v "$PWD":/out \
  alpine tar czf /out/es-snapshot.tar.gz -C /s .

scp es-snapshot.tar.gz пользователь@новая-машина:/tmp/
```

Имя тома можно уточнить через `docker volume ls | grep essnapshots`.

**На новой машине** — `deploy.sh` к этому моменту уже отработал и создал
пустой индекс. Его нужно убрать и положить на его место настоящий.

Шаг 1. Распаковать снимок в том и зарегистрировать хранилище:

```bash
cd /opt/sochi-search

docker run --rm \
  -v sochi-search_essnapshots:/s \
  -v /tmp:/in \
  alpine tar xzf /in/es-snapshot.tar.gz -C /s

curl -XPUT "http://127.0.0.1:9200/_snapshot/move" \
  -H 'Content-Type: application/json' \
  -d '{"type":"fs","settings":{"location":"/snapshots"}}'
```

Шаг 2. Посмотреть, что есть сейчас и что лежит в снимке:

```bash
curl -s "http://127.0.0.1:9200/_cat/indices/sochi_docs_v4_*?h=index,docs.count"
curl -s "http://127.0.0.1:9200/_snapshot/move/_all?pretty" | grep -E '"snapshot"|sochi_docs'
```

Первая команда покажет пустой индекс, созданный `deploy.sh`, — у него в
`docs.count` будет `0`. Вторая покажет имя снимка и имя индекса внутри.

Шаг 3. Удалить пустой индекс. Вместе с ним снимется и alias:

```bash
curl -XDELETE "http://127.0.0.1:9200/<имя пустого индекса>"
```

> Если пустой индекс и индекс из снимка называются одинаково — так
> бывает, когда обе машины разворачивались в один день, — удалить всё
> равно нужно: иначе восстановление упрётся в занятое имя.

Шаг 4. Восстановить и направить на него alias:

```bash
curl -XPOST "http://127.0.0.1:9200/_snapshot/move/full/_restore?wait_for_completion=true" \
  -H 'Content-Type: application/json' \
  -d '{"indices":"sochi_docs_v4_*","include_global_state":false}'

curl -XPOST "http://127.0.0.1:9200/_aliases" \
  -H 'Content-Type: application/json' \
  -d '{"actions":[{"add":{"index":"<имя индекса из снимка>","alias":"sochi_search"}}]}'
```

Шаг 5. Проверить:

```bash
curl -s "http://127.0.0.1:9200/sochi_search/_count"
```

Число должно совпасть с тем, что было на старой машине. Перезапускать
приложение не нужно: alias разрешается при каждом запросе.

### 6.3. Более грубый, но более простой способ

Если версии Elasticsearch на обеих машинах совпадают — а они совпадают,
версия закреплена в `docker-compose.yml` — можно перенести том с данными
целиком. Способ не рекомендован Elastic, но при остановленном кластере
работает и требует меньше шагов:

```bash
# на старой машине
docker compose -f docker-compose.yml stop elasticsearch
docker run --rm -v sochi-search_esdata:/d -v "$PWD":/out \
  alpine tar czf /out/esdata.tar.gz -C /d .
docker compose -f docker-compose.yml start elasticsearch

# на новой машине — до первого запуска Elasticsearch
docker volume create sochi-search_esdata
docker run --rm -v sochi-search_esdata:/d -v /tmp:/in \
  alpine tar xzf /in/esdata.tar.gz -C /d
```

Обязательное условие — Elasticsearch на старой машине **остановлен** во
время архивации. Копия работающего кластера почти наверняка окажется
битой.

### 6.4. Не переносить, а собрать заново

Ничего не требует и не рискует данными, но занимает время:

1. открыть раздел управления;
2. нажать «Обход сайта» — соберёт адреса, около часа;
3. нажать «Разобрать очередь» — скачает и разберёт документы, около суток;
4. распознавание сканов пойдёт фоном, первые две страницы каждого
   документа — за несколько суток.

Дальше всё повторяется само по расписанию.

## 7. Проверка после переезда

```bash
cd /opt/sochi-search
COMPOSE="docker compose -f docker-compose.yml -f docker-compose.app.yml"

# все контейнеры запущены
$COMPOSE ps

# поиск отвечает
curl -s http://10.0.0.5:18084/health/ready

# документы на месте
curl -s "http://10.0.0.5:18084/search?q=благоустройство&limit=1" | head -c 400

# раздел управления пускает по паролю
curl -s -u admin http://10.0.0.5:18084/admin/api/state | head -c 400

# конвейер двигается
$COMPOSE logs --tail 30 worker
```

И глазами, это важнее команд:

- открыть `/ui`, задать три-четыре реальных запроса — например номер
  постановления и пару слов из названия;
- проверить, что фильтры по годам и рубрикам меняют выдачу;
- открыть `/admin`, войти по логину и паролю;
- убедиться, что число документов растёт, а очередь уменьшается.

## 8. Повседневное управление

Всё делается из браузера, в разделе `/admin`. Строкой кода — только то,
чего в разделе нет.

| Что нужно | Как |
| --- | --- |
| Посмотреть состояние | `/admin`, верхний блок |
| Запустить обход или разбор | `/admin`, кнопки задач |
| Посмотреть, что делает задача | `/admin`, «Журнал» рядом с задачей |
| Переиндексировать один документ | `/admin`, «Переиндексировать документ» |
| Перезапустить всё | `$COMPOSE restart` |
| Обновить код | `git pull && $COMPOSE build && $COMPOSE up -d` |
| Остановить всё | `$COMPOSE down` (данные в томах остаются) |

Резервные копии очереди делаются сами раз в сутки контейнером `backup`.

### Крупные файлы

Файлы больше 150 МБ не скачиваются: один такой занимает воркер на
десятки минут и вытесняет из памяти всё остальное. Они помечаются
статусом `skipped_too_large`. Посмотреть список:

```bash
$COMPOSE exec -T api python - <<'PY'
import sqlite3

db = sqlite3.connect("/app/data/crawl_state.sqlite3")
rows = db.execute(
    "SELECT url FROM crawl_urls WHERE status = 'skipped_too_large'"
).fetchall()

print(len(rows), "адресов")
for row in rows[:50]:
    print(row[0])
PY
```

Если такой документ действительно нужен — поднять
`CRAWL_PDF_MAX_DOWNLOAD_BYTES` в `.env`, перезапустить и обработать его
по одному адресу через «Переиндексировать документ».

### Второй проход распознавания

Первый проход распознаёт только первые две страницы каждого скана: там
заголовок, номер и дата, то есть всё, по чему документ ищут. Так весь
корпус становится находимым за несколько суток вместо нескольких недель.

Когда первый проход закончится — в разделе управления «Распознать PDF»
дойдёт до 100 % — можно запустить второй, уже целиком:

```bash
nano .env       # CRAWL_PDF_OCR_COVERAGE_PAGES=0
$COMPOSE up -d ocr-1 ocr-2
```

## 9. Если реестр образов недоступен

В сети за VPN `registry-1.docker.io` часто закрыт. Тогда образы
переносятся файлами с любой машины, у которой есть интернет.

```bash
# на машине с интернетом
docker pull docker.elastic.co/elasticsearch/elasticsearch:8.19.17
git clone <адрес репозитория> sochi-search && cd sochi-search
docker build -t sochi-search-app:2.5.0 .

docker save \
    docker.elastic.co/elasticsearch/elasticsearch:8.19.17 \
    sochi-search-app:2.5.0 \
  | gzip > sochi-images.tar.gz

# перенести файл на целевую машину, затем там:
gunzip -c sochi-images.tar.gz | docker load
```

После `docker load` образы уже на месте, и `deploy.sh` пропустит сборку:
Docker не пойдёт в сеть за тем, что у него есть. Проверить перед
запуском:

```bash
docker images | grep -E "sochi-search-app|elasticsearch"
```

## 10. Что будет дальше

Два будущих направления учтены в устройстве системы заранее — менять её
под них не придётся.

### Бот в мессенджере Max

Боту не нужен доступ к базе или индексу. Поиск уже отдаёт готовый JSON:

```
GET /search?q=<запрос>&limit=5
```

Ответ содержит заголовок, адрес, дату, номер документа, рубрику и
фрагмент текста — ровно то, что бот показывает в сообщении. Есть и поиск
строго по номеру: `GET /search?document_number=512-р`.

Порядок подключения, когда дойдут руки:

1. бот ставится отдельным контейнером в этот же `docker-compose.app.yml`
   и попадает в ту же сеть `sochi-search`;
2. внутри сети он обращается к `http://api:8000/search` — наружу
   открывать ничего не нужно;
3. если Max требует адрес из интернета для webhook, наружу выставляется
   **только бот**, а поиск остаётся во внутренней сети. Бот при этом
   становится единственной точкой входа снаружи, и всё, что он умеет, —
   пересказывать результаты поиска.

Никаких изменений в самом поиске это не потребует.

### Семантический поиск

Сейчас поиск лексический: он находит документы по словам запроса с
учётом морфологии русского языка. Семантический ищет по смыслу — тогда
«где взять справку о составе семьи» найдёт документ, в котором нет ни
одного из этих слов.

Что для этого нужно:

1. **Машина помощнее.** Модель, считающая векторы, требует 2–4 ГБ
   памяти и заметно быстрее работает с видеокартой. На нынешних 8 ГБ
   рядом с Elasticsearch и распознаванием ей места нет.

2. **Новое поле в схеме.** В `elasticsearch/sochi_docs_v4.json`
   добавляется поле типа `dense_vector` — по одному вектору на фрагмент
   текста. Схема уже хранит текст фрагментами по 3500 символов, и это
   ровно тот размер, с которым работают модели: резать заново не
   придётся.

3. **Пересборка индекса.** Через тот же `ops/reindex.py`, которым уже
   делался переход на нынешнюю схему: alias переключается одной
   операцией, поиск при этом не останавливается.

4. **Гибридный запрос.** Лексический и векторный поиск объединяются
   в один запрос с взвешиванием результатов. Меняется только
   `app_v2/search_query.py` — единственное место, где собирается тело
   запроса; остальной код его не касается.

Порядок именно такой: сначала машина, потом поле, потом пересборка,
потом запрос. Работа на неделю-полторы, и её удобно делать после того,
как распознавание пройдёт корпус целиком.

## 11. Если что-то пошло не так

| Что видно | Что делать |
| --- | --- |
| `deploy.sh`: «Демон Docker не отвечает» | `systemctl status docker`, при отказе `systemctl start docker` |
| `env file .env not found` | запустить `bash deploy.sh` — он создаст файл из образца |
| Elasticsearch не поднялся за пять минут | `sysctl -w vm.max_map_count=262144`, затем повторить |
| `bootstrap: max virtual memory areas too low` | то же самое: `vm.max_map_count` |
| Контейнеры перезапускаются по кругу | `$COMPOSE logs --tail 100 <имя>` — в журнале будет причина |
| `/admin` отвечает 503 | не заполнен `ADMIN_PASSWORD_SHA256` в `.env` |
| `/admin` не принимает верный пароль | `ADMIN_COOKIE_SECURE=true` при работе по http — поставить `false` |
| Поиск не открывается с другой машины | `ss -tlnp \| grep 18084` — проверить адрес; затем правила экрана |
| Docker не открывает порт: «cannot assign requested address» | адреса из `API_BIND` нет у машины, сверить с `hostname -I` |
| Поиск отвечает, но ничего не находит | индекс пустой — раздел 6 |
| Мало памяти, всё тормозит | уменьшить `ES_HEAP`, оставить один контейнер распознавания: `$COMPOSE stop ocr-2` |

Журналы всех контейнеров разом:

```bash
$COMPOSE logs --tail 100
```

Полный сброс с сохранением данных:

```bash
$COMPOSE down
$COMPOSE up -d
```

Полный сброс **с удалением данных** — только если решено собирать всё
заново:

```bash
$COMPOSE down -v
bash deploy.sh
```

## Приложение: что осталось на старой машине

Рабочий сервер запускает задачи через systemd, а не через Docker. При
переезде это заменяется контейнерами — роли и интервалы совпадают:

| Было (systemd) | Стало (контейнер) |
| --- | --- |
| `sochi-search-api-v2.service` | `api` |
| `sochi-search-worker.timer` | `worker` |
| `sochi-search-discovery.timer` | `discovery` |
| `sochi-search-pdf-ocr@1.timer`, `@2` | `ocr-1`, `ocr-2` |
| `sochi-search-publication-date.timer` | `publication-date` |
| `sochi-search-content-cleanup.timer` | `content-cleanup` |
| `sochi-search-backup.timer` | `backup` |

Разница одна: контейнер выдерживает паузу **после** окончания прохода, а
таймер systemd запускался по расписанию независимо от того, закончился
предыдущий или нет. Из-за этого долгий проход больше не накладывается на
следующий.

В папке `systemd/` репозитория лежат только drop-in-файлы — поправки к
базовым юнитам. Сами базовые юниты `sochi-search-worker.service`,
`sochi-search-discovery.service`, `sochi-search-publication-date.service`
и `sochi-search-content-cleanup.service`, а также установщик
`install.sh` существуют только на рабочем сервере. Для контейнерного
переезда они не нужны — роли задаёт `entrypoint.sh`, а установку делает
`deploy.sh`. Если когда-нибудь понадобится развернуть проект без Docker,
их надо будет забрать оттуда:

```bash
cp /etc/systemd/system/sochi-search-{worker,discovery,publication-date,content-cleanup}.service \
   /opt/sochi-search/systemd/
```

Рабочий сервер переезд не затрагивает: он продолжает работать как
работал, пока данные не перенесены и новая машина не проверена. Гасить
его стоит только после того, как на новой машине прошли проверки из
раздела 7.
