# Третий проход: чего не хватало для эксплуатации

Первые два прохода разбирали код: что написано неверно, что написано и
не подключено, что расходится с собственными тестами. Этот проход
спрашивал другое — чего в проекте **нет**. Не «что сломано», а «что
обычно есть у систем, которые работают в продуктиве, и чего здесь не
завели».

Разница по последствиям существенная. Ошибка в коде проявляется сама:
рано или поздно кто-то видит неверный ответ. Отсутствие проверки не
проявляется никогда — оно только меняет вероятность того, что следующая
ошибка доедет до сервера.

Ниже — восемь находок. Для каждой: чего не было, чем это обернулось бы
и что сделано. Девятым разделом — три поломки, которые нашёл сам
прогон проверок, на первом же запуске.

---

## 1. Тесты никто не запускал автоматически

В проекте 375 тестов, и среди них редкие по качеству: разбор всего кода
синтаксисом 3.8, согласие двух реализаций нормализации номера,
соответствие флагов systemd тому, что объявляет argparse, проверка
связок между модулями.

Запускалось всё это руками.

Тем, что запускается руками, пользуются, пока помнят. История проекта
показывает, чем это кончается, — и показывает дважды, причём обе записи
есть в README:

- два теста разошлись с кодом и не проходили неизвестно сколько: один
  ждал `DownloadTooLargeError` там, где код давно кидает
  `DocumentTooLargeError`, второй сверялся со строкой `pdf-ocr-v5`, когда
  в коде стояло `pdf-ocr-v6`;
- сам набор не запускался на 3.8 — на той версии, где система работает.
  Три проверки пользовались `ast.unparse` (3.9) и
  `sys.stdlib_module_names` (3.10). На машине разработчика с 3.11 всё
  было зелено.

Ни то, ни другое нельзя увидеть, читая код. Это видно только прогоном.

**Сделано.** `.github/workflows/ci.yml`. Матрица повторяет то, что есть
в жизни, а не «свежий Python»:

| Прогон | Что воспроизводит |
| --- | --- |
| 3.12 с зависимостями | контейнер |
| 3.12 без зависимостей | свежая копия репозитория |
| 3.8 без зависимостей | Python рабочего сервера |
| сборка образа | выкладка |

Последняя строка ловит то, чего не видит ни один тест: несобираемый
Dockerfile, пропавший пакет apt, зависимость, которая больше не
ставится. Всё это сейчас выясняется при выкладке, то есть в худший
момент.

Матрица тоже может устареть — достаточно поднять Python в Dockerfile.
Поэтому `ContinuousIntegrationTests` берёт версии из самих файлов: из
`FROM python:` и из README. Разъедутся — проверка потребует поправить.

## 2. Два модуля тестов падали вместо пропуска

Роль `tests` в образе обещает прямо: «тесты, которым нужны отсутствующие
библиотеки, объявляют пропуск сами, поэтому перечислять модули руками не
нужно».

Обещание держалось не везде. `test_ocr_engine` и `test_v250_units`
импортировали numpy и Pillow сразу за `import unittest`. На свежей копии
репозитория `unittest discover` показывал:

```text
Ran 261 tests
FAILED (errors=2, skipped=7)
```

Ошибка загрузки модуля — это не «два теста не прошли». Это ненайденные
тесты. В `test_v250_units` вместе с семью проверками подготовки
изображения молча выпадали сорок проверок построителя запроса, схемы
индекса и разбора ответа — тех, которым никакие библиотеки не нужны
вовсе. Набор при этом выглядел красным, а не неполным, и понять разницу
можно было только вручную.

**Сделано.** `test_ocr_engine` объявляет пропуск целиком: он импортирует
`pdf_ocr_engine`, а тот тянет numpy через `pdf_ocr_image` — без
библиотеки проверять там нечего. В `test_v250_units` под пропуск ушли
ровно три класса, которым нужно изображение; остальные сорок проверок
работают.

Защита — `SuiteLoadsWithoutOptionalLibrariesTests`. Она проверяет
поведение, а не форму записи: набор запускается заново в отдельном
процессе, где перечисленные библиотеки объявлены отсутствующими, и в
выводе не должно быть ни одной ошибки загрузки. На старом коде проверка
падает и называет оба модуля по именам.

## 3. У большинства зависимостей не было верхней границы

```text
fastapi
uvicorn[standard]
requests
beautifulsoup4
lxml
pymupdf
...
```

Образ собирается командой `pip install --requirement requirements.txt`.
Без верхней границы каждая пересборка тянет то, что вышло к этому дню.
Выкладка правки в одну строку становится обновлением половины
зависимостей — молча и в момент, когда чинят что-то другое.

Проект уже знает этот класс отказа и описал его в README: `mode=` у
`Image.fromarray` объявлен устаревшим и исчезает в Pillow 13, выпуск
которой назначен на 15 октября 2026 года. Там границу поставили. В
остальных одиннадцати строках — нет.

**Сделано.** Границы у всех: нижняя — то, на чём проверено, верхняя —
следующий мажорный выпуск. `test_every_requirement_has_an_upper_bound`
не даёт добавить новую строку без границы.

Обратная сторона понятна: закреплённые версии не обновляются вообще, и
через год проект стоит на выпусках, в которых с тех пор чинили и
уязвимости. Поэтому вторая половина решения — `.github/dependabot.yml`:
обновления приходят отдельными правками, CI их проверяет, принимает
человек. Граница поднимается сознательно, а не как побочное следствие
пересборки.

## 4. Журналы контейнеров росли без предела

Драйвер `json-file` — умолчание Docker — предела не имеет. Файл растёт,
пока не кончится место.

Здесь это не абстракция. Семь контейнеров работают непрерывно; разбор
очереди и распознавание печатают строку прогресса на документ; на
машине 20 ГБ, и на них же лежит индекс на восемь. Заполненный диск
останавливает и Elasticsearch, и обход, причём выглядит это как отказ
кластера, а не как переполнение, — то есть чинят сначала не то.

**Сделано.** Предел в обоих файлах compose: три файла по 20 МБ на
контейнер, около 420 МБ на всё развёртывание, примерно неделя журналов
при нынешнем темпе. Значения вынесены в `LOG_MAX_SIZE` и
`LOG_MAX_FILES`.

## 5. Шесть контейнеров из семи были вечно unhealthy

`HEALTHCHECK` объявлен в образе:

```dockerfile
HEALTHCHECK CMD curl -fsS "http://127.0.0.1:${APP_PORT:-8000}/health/live"
```

Образ у всех ролей один, а порт 8000 слушает только `api`. Остальные
шесть — `worker`, `discovery`, `ocr-1`, `ocr-2`, `publication-date`,
`backup` — раз в тридцать секунд стучались в закрытый порт и получали
статус `unhealthy` навсегда.

Работающая система показывалась сломанной. Хуже другое: присмотр по
статусу контейнера — то, ради чего `HEALTHCHECK` и заводят, — терял
всякий смысл, потому что красное там было всегда.

**Сделано.** Роли без HTTP-порта отключают проверку явно
(`healthcheck: disable: true`). У `api` она остаётся и означает то, что
должна.

Заодно исправлено соседнее: у Elasticsearch проверки готовности не было
вовсе, а `depends_on` стоял без условия. `docker compose up -d` отвечал
«поднято» через секунду, когда кластер ещё разворачивал шарды. Теперь
кластер объявляет готовность сам (`wait_for_status=yellow` — на
одноузловом кластере `green` не наступает никогда), а приложение ждёт
её.

## 6. Индекс не попадал ни в одну автоматическую копию

Самая дорогая находка прохода.

Ежедневная копия (`ops/backup.py`) забирает очередь SQLite и код.
Индекса в ней нет. Обоснование выглядит убедительно: индекс —
производное, очередь цела, значит документы можно разобрать заново.

Обоснование неверно, и вот в каком месте. «Заново» — это не
«перекачать», а **перераспознать**. Большая часть корпуса — сканы без
текстового слоя. По собственным замерам проекта: первый проход по двум
страницам каждого документа — 26 часов, полный корпус — недели работы
обоих слотов OCR.

То есть потеря тома Elasticsearch стоит не часов, а месяца — против
часа восстановления из снимка.

Механизм для снимков в проекте уже был целиком: `path.repo: /snapshots`
и том `essnapshots` объявлены в compose, `docs/DEPLOY.md` подробно
описывает, как снять и восстановить, и даже есть тест, проверяющий, что
хранилище настроено. Не было ровно одного — чтобы это происходило само.
Процедура переезда выполняется раз в год, при переезде. Копия нужна в
тот день, когда её никто не собирался делать.

**Сделано.** `ops/snapshot.py`: регистрация хранилища, снимок с
ожиданием завершения, уборка старых. Роль `backup` в контейнере делает
за проход обе копии; для установки без Docker добавлены
`sochi-search-snapshot.service` и `.timer`.

Три решения, каждое из которых могло быть принято иначе:

**Уборка трогает только свои снимки.** Удаляются те, чьё имя начинается
с `auto-`. Снимок, снятый руками перед переездом, переживёт любое число
ночных запусков. Автоматическая задача, удаляющая то, что человек снял
намеренно, — это не уборка.

**Неудачный снимок не запускает уборку.** Если хотя бы один шард не
попал в снимок, задача обрывается до удаления старых. Иначе исход был бы
такой: годных копий стало меньше, негодная добавилась. Это хуже, чем не
иметь задачи вообще.

**Хранилище, указывающее не туда, — отказ, а не перерегистрация.**
`path.repo` задаётся в compose, и при переносе на машину с другим путём
молчаливая перерегистрация оставила бы систему с пустым хранилищем и
уверенностью, что копии есть.

**Почему не SLM.** У Elasticsearch есть встроенное управление снимками
по расписанию, и в бесплатной лицензии оно доступно. Отказ сознательный:
политика SLM — это состояние внутри кластера. Его не видно из
репозитория, оно не проверяется тестами и теряется вместе с кластером —
ровно в том случае, ради которого всё и делается. Здесь та же работа
описана кодом, запускается той же ролью, что и остальные задачи, и
покрыта 32 тестами.

Чего это по-прежнему не решает: том `essnapshots` лежит на той же
машине. При отказе диска целиком снимки уйдут вместе с индексом. Копия,
переживающая машину, — это выгрузка тома в файл, и она остаётся ручной
процедурой из `docs/DEPLOY.md`. Автоматизировать её означало бы завести
в проекте вторую машину, которой нет.

## 7. Из резервной копии нельзя было поднять систему

Список того, что кладётся в копию, отвечает на один вопрос: хватит ли
этого, чтобы поднять систему на чистой машине?

Не хватало. В копию попадал код — и не попадало то, чем он запускается:

- `Dockerfile`;
- `docker-compose.app.yml`, где описаны все семь ролей;
- `docker/entrypoint.sh`;
- `deploy.sh`;
- `systemd/` целиком;
- `VERSION`.

Восстанавливающий получал исходники и собирал окружение заново по
памяти — в тот день, когда времени на это меньше всего.

Отдельная деталь: первой строкой в списке стоял пакет `app` — первая
версия сервиса, удалённая ещё в прошлом проходе. Несуществующие записи
копирование пропускает молча (`if source.exists()`), поэтому строка
ничего не ломала и просто не значила ничего. Это тот самый признак, по
которому список перестают читать: в нём есть заведомо мёртвая запись, и
никто этого не замечает.

**Сделано.** Список приведён в соответствие с тем, что нужно для
запуска. `RestorableSourceTests` проверяет его с двух сторон: всё
необходимое для запуска в нём есть, и всё, что в нём есть, существует в
репозитории.

## 8. Обходчик представлялся сайту чужой версией

Единственная строка проекта, которую видит чужая сторона, — `User-Agent`
обходчика. Она стоит напротив каждого запроса в журналах `sochi.ru`.

Значений было два, и оба неверные:

| Где | Значение |
| --- | --- |
| `.env.production.example` | `SochiSearch/2.5.0` |
| `crawler_v2/config.py` (умолчание) | `SochiSearchBot/2.0` |
| `VERSION` | `2.6.0` |

Проверка согласия версий в проекте есть, и хорошая. Но она перечисляла
места по одному — пять штук, — и оба места про `User-Agent` в перечень
не попали. Причём её собственная docstring говорила «в шести местах».

Последствие скромное, но неприятное: если бы администратор `sochi.ru`
захотел понять, что за обходчик ходит по сайту и с кем говорить, он
увидел бы имя, которого в проекте нет, и версию трёхлетней давности.

**Сделано.** Оба значения — `SochiSearch/2.6.0`, оба добавлены в
проверку согласия. Мест в ней теперь восемь.

## 9. Что нашёл сам прогон, на первом же запуске

Эту часть стоит прочитать целиком: она — лучший аргумент в пользу
первой находки.

Всё выше проверялось локально, и локально было зелено. Прогон на
GitHub упал сразу, тремя разными способами, и все три оказались
настоящими.

### Заглушки одного теста ломали другой

`test_crawler_runtime` кладёт в `sys.modules` собственные заглушки
`requests` и `urllib3`, если настоящих нет. Заглушками были
`Session = object`, `HTTPAdapter = object`, `Retry = object`.

`sys.modules` один на процесс, поэтому заглушки достаются всему, что
импортируется позже. `app_v2/es_http.py` при импорте создаёт клиента и
вызывает `Retry(total=2, connect=2, ...)` — а `object()` аргументов не
принимает. Падал `test_document_titles`, с сообщением
`object() takes no arguments` и трассировкой, в которой нет ни слова
про заглушки.

Из-за этого не грузился целый модуль, то есть двадцать проверок не
находились вовсе.

Увидеть это можно было только там, где библиотек действительно нет.
Ни на машине разработчика, ни в контейнере таких условий не бывает —
поэтому за всё время никто и не увидел. Заглушки заменены на класс,
принимающий любые аргументы.

### Проверка про PyMuPDF отвечала не на свой вопрос

`test_search_service_imports_without_pymupdf` запускает дочерний
процесс и убеждается, что поиск импортируется без PDF-библиотеки. Без
`requests` дочерний процесс падал — но по другой причине, и тест
сообщал о провале так, будто дело в PyMuPDF.

Причём наивная защита (`try: import requests`) здесь не работает:
заглушка соседнего модуля уже лежит в `sys.modules`, и импорт проходит.
Различать приходится по `__file__`, которого у заглушки нет, — тем же
приёмом, который в `tests/test_large_pdf_fetch` уже был описан для bs4.
Проект знал про эту ловушку и всё равно в неё попал ещё раз.

### Внутри образа набор не был зелёным никогда

Роль `tests` в образе обещает прогон «тем же образом, что и в работе»,
и README предлагает её как способ проверки. На деле она давала
восемь провалов и девятнадцать ошибок.

Причина не в коде: образ копирует только то, что нужно работе —
пакеты, схему индекса, языковые модели, тесты. Ни `docker-compose.app.yml`,
ни `systemd/`, ни `Dockerfile` в нём нет и быть не должно. А два
десятка проверок читают именно эти файлы.

То есть проверки спрашивали про файлы, которых там нет по замыслу, и
выглядело это как двадцать поломок. Двадцать из них существовали до
этого прохода; ещё несколько добавил он сам, когда завёл проверки
compose и матрицы.

Такие проверки теперь объявляют пропуск через `requires_repository` из
`tests/compat.py`. В образе набор проходит: 375 тестов, 46 пропусков, и
каждый пропуск говорит правду — договорённости про запуск проверяются
там, где есть чем.

### Что из этого следует

Три поломки, ни одна из которых не видна из кода. Первая жила ровно до
того дня, когда набор впервые запустили на машине без библиотек.
Вторая — до того, как первая перестала её заслонять. Третья была видна
всегда, стоило один раз запустить `docker run ... tests`, — и именно
поэтому её никто не видел.

Прогон, который случается сам, отличается от прогона, который надо не
забыть, ровно этим.

Итог по трём средам:

| Среда | Тестов | Пропущено |
| --- | ---: | ---: |
| Репозиторий, библиотеки установлены | 375 | 5 |
| Репозиторий, ничего не установлено | 354 | 23 |
| Внутри образа | 375 | 46 |

## Что осмотрено и сознательно не сделано

Не всё, чего в проекте нет, стоит заводить. Ниже — то, что проверялось
и оставлено как есть, с причиной.

**Ограничение частоты запросов к API.** Обычная вещь для публичного
поиска. Здесь порт открывается только на адрес внутренней сети
(`API_BIND`), пользователей десяток-другой, а `/search` и `/answer` уже
ограничены сверху по `limit` и глубине выдачи. Городить ограничитель
ради внутренней сети — это код, который нужно поддерживать, ради риска,
которого нет.

**`/metrics` для Prometheus.** Тоже обычная вещь — но Prometheus в
контуре нет. Эндпоинт без того, кто его опрашивает, это не наблюдаемость,
а строчка в README. Состояние конвейера уже отдаёт `/pipeline/status`, и
его читает раздел управления. Заводить стоит вместе со сбором, а не
вперёд него.

**Проверка `robots.txt` в разборщике очереди.** Сейчас `robots.txt`
читает обход (`discovery_worker_v2`), и адрес не попадает в очередь,
если он запрещён. Разборщик очереди проверку не повторяет. Дыра
теоретическая: адрес, разрешённый вчера и запрещённый сегодня, будет
перечитан в течение `CRAWL_RECHECK_HOURS`. Стоимость исправления —
разбор `robots.txt` в каждом воркере плюс его кэширование; выгода — на
одном сайте, который сам же и заказал систему, околонулевая. Записано,
не сделано.

**Файл лицензии.** В репозитории его нет, и README называет код
портфолио. Без файла лицензии это «все права защищены»: посмотреть
можно, использовать — нет. Выбор лицензии — решение владельца, а не
следствие аудита, поэтому здесь он только назван.
